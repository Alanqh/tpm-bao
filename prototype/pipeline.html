一句话

请求全程产生日志；判定瞬间产生事件（秒级）；分钟闭合时聚合产生指标（分钟级）。三种数据、三类存储、三套查询，页面上每个元素都有明确来源。

本页说明「资源包监控」（前台 usage.html 与后台 admin-usage.html）页面上的每一条数据，从请求进入网关到出现在图表上，分别经过哪些阶段、在哪个时点提取、如何聚合、如何形成事件、如何存储。

1 · 链路总览

一条 API 请求进入平台后，监控数据按「三个出口」流出：

请求 ──► 网关（路由/归属）──► 限流器（60s 滑动窗口判定）──► 缓存查询 ──► 推理（首 token / 流式）──► 响应完成 │ │ │ ├─(即时)──► 事件 events（秒级：429 限流） ├─(全程逐字段)────────────────────────────────────────► 日志 logs（单请求全字段） │ │ └─(延迟到整分钟闭合)──────────────────────────────────► 指标 metrics（分钟桶：vTPM / TTFT / TPOT / 5xx）
出口写入时机时间粒度数据形态
事件 events 判定发生的那个瞬间（如限流器拒绝请求的时刻） 秒级（HH:MM:SS） 一条告警性质的结构化记录，携带判定依据（窗口值）与关联请求 ID
日志 logs 响应完成（或被拒绝）时一次性落盘 单请求 rid、状态码、TTFT/TPOT、token 数、cache 命中等全字段
指标 metrics 自然分钟闭合时（每分钟第 0 秒触发）批量聚合 分钟级 该资源包该分钟的桶值（求和 / 分位数 / 计数）

为什么 429 红点和分钟柱「不同源」：429 是请求进入限流器那一刻的即时判定，事件即时生成、时刻精确到秒；分钟柱是分钟闭合时对成功请求的事后聚合。两者产生时刻不同、口径不同（窗口值 vs 分钟求和），所以同一分钟里红点的高度与柱顶不需要一致。

2 · 单个请求：各阶段提取什么

下表按请求生命周期逐段说明：每个阶段发生在什么时点、提取哪些指标、这些指标后续流向哪里（事=写事件、日=写日志、指=等分钟闭合进指标、日+指=同时进日志与指标）。

阶段 发生时点 提取的内容 流向
网关路由 请求进入（t₀） model_name → 资源包 Pool 的绑定关系、计费归属（预留 or Serverless 兜底） 日
限流器判定 推理前，瞬时 以「进入时刻」向前取 60s 滑动窗口的历史 token 流量求得的窗口 vTPM，与购买量比较；不落历史库（仅判定瞬间存在），若超限则连同窗口值写事件 事日
缓存查询 推理前 前缀 cache 命中 token 数 / 未命中 token 数（决定实算部分） 日
首个 token 流式开始 TTFT = 首 token 时刻 − t₀（ms） 日+指
逐 token 生成 流式过程 TPOT = 相邻 token 平均间隔（ms），累计输出 tokens 日+指
响应完成 流结束 状态码（2xx / 429 / 5xx）、输入+输出 tokens 合计、请求时长 日+指
分钟闭合 下一分钟第 0 秒 对本分钟内所有请求的原始点做聚合（见第 4 节），生成分钟桶 指

429 请求没有「推理阶段」。它在限流器就被拒绝，不会产生 TTFT/TPOT/tokens，因此分钟柱（对这些求和）天然不包含 429 请求——被拒绝的请求没有消耗预留算力。

4 · 聚合：怎么从原始请求变成分钟数据

聚合只发生在分钟闭合这一个时刻（每小时第 x 分 0 秒触发，处理前一分钟的原始点），规则按指标口径分开：

指标 聚合公式 参与样本 为什么这样聚合
vTPM 分钟柱 Σ(请求 tokens)，分钟内求和 本分钟成功请求（2xx）的 in+out tokens；429 不计 柱子表达的是「这一分钟实际消耗了多少预留吞吐」，被拒绝的请求没有消耗
TTFT P95(请求 TTFT) 本分钟成功请求的首 token 时延样本 分位数比均值更能反映长尾体验，与 SLA 阈值 120ms 直接比较
TPOT P95(请求 TPOT) 本分钟成功请求的 token 间隔样本 同上，阈值 25ms
5xx 数量 Count(状态码 ≥ 500) 本分钟全部响应完成的请求 分钟级计数呈现趋势；429 属于 4xx，不混入
滑动窗口 vTPM ——不聚合。它只在限流器判定瞬间计算，只随 429 事件落入 events；metrics 分钟桶中不存在任何窗口值

聚合的去噪设计：分钟桶写完即不可变（幂等重算），时区按资源包归属地取自然分钟；跨分钟的请求（跨 14:33:00 未结束）归属结束时刻所在分钟，避免双计。

5 · 事件：怎么形成、字段是什么

事件不是聚合出来的，而是判定规则命中时即时生成。分两类：

类别 生成时机 时间戳 触发条件与携带字段
即时类
（throttle 429）		 限流器拒绝请求的瞬间 秒级 窗口 vTPM > 购买量。字段：occur_at（HH:MM:SS）、window（60s 窗口值）、购买量、超出量、rid（被拒请求）、pool、model
闭合类
（SLA 违约、5xx 集中）		 分钟闭合、聚合完成后判定 分钟级 TTFT 分钟 P95 > 120ms → B 类违约；TPOT P95 > 25ms → B 类；本分钟 5xx 计数 ≥ 3 → C 类。字段：occur_at（分钟）、对应的分位值/计数、pool

同一分钟内多次 429 的处理

  • 存储层：每次触发都独立写一条事件，全量保留、可全量检索（事件大表按时间倒序完整列出）。
  • 展示层：红点以分钟为横轴单位，一分钟只画 1 个点——取该分钟内窗口值最高的 1 条（峰值最有代表性），点的高度锚定该条的窗口值而非分钟柱高度；其余事件在悬停浮层中逐条列出（时刻 + 窗口值）。
  • 这是纯展示规则，不修改、不合并存储数据。

6 · 存储：metrics / events / logs 三库

按「查询模式」分离存储，一份数据不重复承担两种读写特征：

库 写路径 粒度 / 键 保留期 读模式（页面如何查询）
metrics
分钟桶时序		 分钟闭合批量写入，一次一行 分钟 / (pool, minute) 90 天 渲染图表直读时间范围；体积小（1 点/分钟/包），长期保留支持回看 7d/30d
events
事件表		 判定瞬间追加（429），或分钟闭合后追加（SLA/5xx） 秒或分钟 / (pool, occur_at) 90 天 按时间范围 + 类型 + pool 过滤，支撑事件大表与红点（红点点位查询 group by 分钟取 max window）
logs
请求日志		 响应完成时一行落盘（含被拒的 429 行） 单请求 / rid 7 天 按时间范围扫表 + rid/状态码/模型筛选；体积最大，短保留，明细下钻只覆盖近期

为什么 logs 只留 7 天：原始日志量比聚合结果大 3~4 个数量级（每次请求一行 vs 每分钟一行）。图表回看 90 天靠的是「体积小可长留」的 metrics/events；要看 7 天前某个请求的明细，需要提前导出。

7 · 呈现：页面元素与数据源的对应

「资源包监控」页（前台 usage.html / 后台 admin-usage.html）上每个元素的来源一览：

页面元素 数据源 粒度 取数说明
vTPM 分钟柱（主图） metrics 分钟 直读分钟桶 tokens 求和列
429 红点 + 悬停浮层 events（即时类） 秒 / 图上按分钟峰值 group by 分钟取 max(window)；浮层列出该分钟全部事件与所在分钟 vTPM（注明不同源）
TTFT / TPOT 折线 + SLA 阈值线 metrics 分钟 P95 序列；阈值线为购买 SLA 常量
5xx 分钟柱 metrics 分钟 status ≥ 500 计数列
事件大表（事件 Tab） events 全量 时间倒序 + Tab（违约/限流/系统）+ 时间筛选 + 搜索联动
请求日志表（日志 Tab） logs 单请求 前台列：时刻/rid/状态码/vTPM/TTFT/TPOT/备注；后台扩展列：cache 命中/未命中、输出 tokens、是否限流
SLA 赔付规则表（后台） 配置 — 静态规则，与闭合类事件的违约分类（A/B/C）对应

同一分钟的数值可能不相等，这是口径正确的表现：分钟柱 = 该分钟成功请求 tokens 之和（metrics）；红点高度 = 某次触发前 60s 窗口值（events，秒级）；日志表里那一行 = 单个请求明细（logs）。三者回答的是三个不同的问题——消耗了多少、何时被限、哪个请求出的问题。
